# NAJ「公文録・明治９年」取り込みの記録（2026-10-28）

ArchivesSpace 4.2.1（手元、proxy 経由 http://127.0.0.1:8090/）に、国立公文書館（NAJ）の目録を入れて、そのままで何が起きるかを測った。
スクリプトは `eval/import_naj.py`（`--mode naive` はそのまま写す、`--mode fixed` は手当てあり。`--reset` で NAJ リポジトリの資料群だけ消して作り直す）。
弾かれたものの記録は `data/naj/import-errors-naive.jsonl`（検証エラーは 0 件で空）。

## 入れたもの

リポジトリ NAJ（repo id 6）。資料群 1（Resource）、簿冊 283（Archival Object, level=file）、件名・細目 6,162（その子, level=item）。合計 6,446 件。
作成者は agent「太政官」1 件を全件にリンク。IIIF マニフェストは外部リンク（external_documents）で付けた（簿冊 3 件、件名 120 件は元データに無い）。
Resource の識別子は元データに無いので、id_0=NAJ, id_1=568359（資料群の URI の番号）とした。簿冊・件名の識別子（公01877100、公01877100-06900）は component_id にそのまま入れた。

## そのまま（naive）で起きたこと

1. 検証エラーは 1 件も出なかった。日付・識別子・標題（最大 101 字。別に 300 字のダミーも通る）・component_id のどれも拒否されなかった。
   「拒否されるはず」と予想した論点は、ほぼ外れた。弾かれないぶん、問題は表示に出た（次項）。
2. 日付の意味のずれ（簿冊 283 件のうち、元データの終了日が開始日より粗い・前にあるもの 151 件）。
   元データは「開始 1876-11、終了 1876」のように、終了が年だけのものが多い（開始 年月 202、年のみ 81／終了 年のみ 232、年月 51）。
   ArchivesSpace は begin=1876-11, end=1876 を受け付け、画面に「1876-11 - 1876」「1876-11-1876」（管理画面の階層ツリー）と出す。読むと終了が開始より前に見える。
   確かめたところ、検証は「同じ精度で end が begin より前」だけを拒否する（1876-11 / 1876-03 は `dates/0/end: must not be before begin` で 400）。
   精度が違う組み合わせ（1876-11 / 1876）は素通りする。月が不正（1876-13）は `not a valid date` で 400。
   元データの終了「1876」が「その年の終わり」なのか「開始と同じ年」なのかは、データだけでは分からない（未確認）。
3. 並び順。階層ツリーも公開画面の「コレクションの編成」も、投入した順に並ぶ。元データ（SPARQL 結果）の順は不規則で、
   簿冊は「第百四十七巻、第八十四巻、第二百十一巻…」、件名も識別子順ではなかった。283 簿冊の一覧が、巻の順に読めなかった。
   ArchivesSpace は識別子で自動整列しない（component_id は表示するだけ）。
4. 階層ツリー。簿冊 283 は 200 件ずつ 2 つの区切りで読み込まれ、`tree/root` の応答は 0.07 秒。件数が多くて使えない、ということは起きなかった。
   ただし簿冊の公開画面に「完全な数量: 記録群から継承 283 冊」と出る。資料群に入れた数量（283 冊）が、全部の簿冊に継承されて出る。
5. 作成者 agent は全リポジトリ共通。再実行で同じ名前を作ると `Agent must be unique`（400）。スクリプト側で既存を使うようにした。
6. 取り込み中に別の作業で archivesspace コンテナが再起動され（この作業の指示ではない）、その間の 113 件が 502（nginx Bad Gateway）で失敗した（簿冊 74、件名 39）。
   データの問題ではない。スクリプトに「5xx は 10 秒待って最大 6 回やり直し、4xx は出し直さない」を足した。
   その後の 2 回でも 6〜7 回のやり直しが出たが、原因は未確認。
7. 公開画面の検索に「Translation missing: ja.search-limits.archival_object」が出た（検索条件の行）。
   こちらが付けた URL の `limit=archival_object` による可能性があり、日本語ロケールの訳漏れかどうかは未確認。

## 手当て（fixed）

- 並び順: 簿冊も件名も識別子順に投入。ツリー先頭は「公01724100（第一巻）、公01725100…」、件名も「…-00100、-00200…」の順になった。ArchivesSpace 側の設定ではなく、投入順（データ側の手当て）で解決。
- 日付: 終了が開始より粗い・前のものは end を捨て（date_type=single）、元の表記を expression に「1876-11/1876」の形で残す。画面は expression を表示する。
  ただし「何を意味するか」はまだ分からないので、end を捨てた情報は日付の構造からは検索できなくなる。
- 本体のコード・設定は変えていない。

## 時間

- 投入（API を 1 件ずつ順に POST）: naive 772 秒（6,445 件、約 8.3 件/秒）、fixed 939 秒（約 6.9 件/秒、やり直し待ちを含む）。
- 管理画面の検索（Solr）への反映は、投入の終了時点でほぼ追いついていた（直後 6,271 件、15 秒後に 6,445 件）。
- 公開画面の索引は遅れる。投入終了の約 3〜4 分後に 6,445 件になった（途中の値は 5,614、5,931）。
- 資料群の削除（--reset）: 6,445 件の資料群で 14.7 秒。

## 表示の確認

管理画面と公開画面のスクリーンショットで確かめた（naive と fixed の両方）。スクリーンショットは、別のサイト用の外観で撮ったため公開していない。
件名のページ単体のスクリーンショットは撮っていない（簿冊ページのツリーに件名が並ぶ状態までは確認）。

## 残った問題

- 終了日の意味（上記 2）。国立公文書館に確認するか、元の目録・画像で確かめる必要がある。
- 簿冊に出る「記録群から継承 283 冊」の数量表示（上記 4）。数量を資料群に入れない選択もあるが、試していない。
- IIIF は外部リンクで付けただけ。画像ビューアーでの表示は試していない。
- 公開画面の検索の訳漏れ（上記 7）は切り分けていない。
- 6 の再起動後のやり直しが出る原因は未確認。

## 論文に書ける知見の候補

- 「入れられなかった」ではなく「入ったが意味が壊れた」: ArchivesSpace の日付検証は同じ精度の逆転しか見ず、精度違いの「1876-11 / 1876」は通って、画面に逆転した範囲として出る（元データ 283 簿冊中 151 件）。
- 並び順は ArchivesSpace が識別子でそろえてくれない。ソースの出力順が不規則だと階層ツリーが巻の順に読めない。投入側で識別子順に直すだけで解決する（設定の変更は不要）。
- 6,445 件を API で順に入れるだけで 13〜16 分、管理画面の索引は直後に追いつき、公開画面の索引は 3〜4 分遅れる。画面を確かめるまでの待ち時間として運用に関わる。
- 件数規模（簿冊 283 × 件名 6,162）では階層ツリーは問題なく動く（200 件ずつの分割読み込み、ルートの応答 0.07 秒）。弱点は規模ではなくデータの意味と順序だった。
- 外部サービス（IIIF）へのリンクは、簡単な方法（external_documents）なら 1 件 1 POST で済むが、ArchivesSpace の画面上でビューアーとして使えるわけではない。
